## 3　用户与权限模块（M01）设计说明

### 3.1 模块描述

本模块实现《需求说明书》FR-01：学号/工号注册、登录认证、密码重置、个人中心与角色权限管控，是全部业务接口的鉴权基础。后端程序单元为 routers/auth.py、services/user_service.py、repos/user_repo.py；客户端程序单元为登录/注册页 F01、个人中心页 F02 及 UserViewModel。涉及数据表：t_user（用户）、t_dict（角色字典）、t_operation_log（登录日志）。角色采用 RBAC 模式：客户端按角色控制页面入口显示，后端按依赖注入统一校验，双重保证。

### 3.2 性能

1. 登录接口响应不超过1.5秒（含密码散列验证与 JWT 签发）；
2. 密码散列采用 PBKDF2-HMAC-SHA256，迭代100000次，单次验证耗时控制在100毫秒左右；
3. 连续登录失败5次锁定账号10分钟（对应《需求说明书》FR-101-2）；
4. JWT 有效期30分钟，无操作自动失效（NFR-S6）；token 签发耗时不超过50毫秒。

### 3.3 输入项

**表3　用户与权限模块输入项**

| 输入项 | 格式与取值范围 | 校验规则 | 来源 |
| :--- | :--- | :--- | :--- |
| 学号/工号 | 8～12位数字或字母数字 | 全局唯一，注册时查重（t_user.user_no） | F01 注册页 |
| 密码 | 8～32位，须包含字母和数字 | 长度与复杂度校验；存储前加盐散列 | F01 |
| 确认密码 | 与密码一致 | 两次输入一致性校验 | F01 |
| 姓名/学院/专业 | 字符串，姓名≤20字 | 必填校验 | F01 |
| 联系方式 | 11位手机号 | 正则校验 ^1[3-9]\d{9}$ | F01 |
| 登录账号+密码 | 已注册学号/工号＋密码 | 账号存在性、账号状态（启用/锁定）校验 | F01 登录页 |
| 重置信息 | 学号/工号＋预留手机号＋新密码 | 账号与手机号匹配校验 | F01 重置入口 |

### 3.4 输出项

**表4　用户与权限模块输出项**

| 输出项 | 格式/内容 | 说明 |
| :--- | :--- | :--- |
| 访问令牌 | JWT 字符串（header.payload.signature） | HS256 签名，payload 含 user_id、role、exp（30分钟） |
| 用户信息 | JSON：user_no、姓名、角色、学院、专业、联系方式、违约次数、状态 | 登录后返回并缓存于 UserViewModel |
| 统一返回体 | { code, message, data } | 成功 code=200；失败返回 400/401/409/423 等 |
| 角色列表 | JSON 数组：编码、名称 | 来自 t_dict（type=role），供注册页选择 |

### 3.5 算法

1. 密码散列算法：注册时生成16字节随机盐 salt，计算 hash＝PBKDF2(password, salt, 100000)；存储字段为“salt＋hash”拼接的十六进制串；登录验证时按相同参数重算并恒时比较（防止时序攻击），不存明文（NFR-S1）；
2. JWT 签发与校验算法：header={alg:HS256, typ:JWT}，payload={user_id, role, exp:now+1800}；签名密钥取自配置文件（core/config.py）；校验时验证签名与 exp，失效返回401；
3. 登录失败锁定算法：t_user 维护 fail_count 与 lock_until 字段；失败时 fail_count＋1，达到5次置 lock_until＝now＋10分钟并返回423；锁定期内拒绝登录；登录成功后 fail_count 清零。

### 3.6 流程逻辑

注册流程：录入信息 → 客户端校验（格式、两次密码一致）→ POST /api/auth/register → 服务端查重（学号/工号唯一）→ 生成盐与散列 → 事务写入 t_user（违约次数初始0、状态启用）→ 写操作日志 → 返回成功，跳转登录页。

登录流程：录入账号密码 → 客户端校验 → POST /api/auth/login → 检查锁定状态 → 查询 t_user → 密码散列验证 → 失败则计数并返回401，成功则清零计数、签发 JWT、写登录日志 → 客户端缓存 token 与用户信息，按角色进入对应主界面（管理员进入后台工作台，师生进入设备浏览页）。

**表5　用户与权限模块接口**

| 方法 | 接口路径 | 主要参数/请求体 | 返回/说明 |
| :--- | :--- | :--- | :--- |

| POST | /api/auth/login | 账号、密码 | JWT＋用户信息；423 表示账号锁定 |

## 4　设备与实验室资源模块（M02）设计说明

### 4.1 模块描述

本模块实现《需求说明书》FR-02：实验室与设备台账维护、分类导航、关键词搜索、设备详情与可预约时段展示。后端程序单元为 routers/resource.py、services/resource_service.py、repos/resource_repo.py；客户端程序单元为设备浏览页 F03、设备详情页 F04 及 EquipmentViewModel（含时段日历组件）。涉及数据表：t_lab、t_equipment、t_dict（设备类别）、t_reservation（时段占用来源）。设备状态字典：空闲、已预约、使用中、维护中。

### 4.2 性能

1. 设备列表/搜索在设备规模1000条以内响应不超过1秒（NFR-P2），依赖 t_equipment 设备编号唯一索引与（所属实验室、类别）组合索引；
2. 时段日历查询不超过800毫秒，一次返回近14天占用数据；
3. 分页固定每页10条（客户端可切换20条），总页数随返回体下发。

### 4.3 输入项

**表6　设备与实验室资源模块输入项**

| 输入项 | 格式与取值范围 | 校验规则 | 来源 |

| 实验室筛选 | 实验室ID（整数）或“全部” | 存在性校验 | F03 筛选栏 |
| 类别筛选 | 类别编码（t_dict，type=equipment_type） | 字典校验 | F03 筛选栏 |

### 4.4 输出项

**表7　设备与实验室资源模块输出项**

| 输出项 | 格式/内容 | 说明 |
| :--- | :--- | :--- |
| 设备列表 | JSON：{total, page, list[{设备ID、编号、名称、型号、类别、实验室、状态}]} | 状态由最近有效预约实时推导 |
| 设备详情 | JSON：全部字段＋技术参数＋用途说明＋注意事项 | F04 展示 |
| 时段占用表 | JSON：14天×每日槽位数组，槽位粒度30分钟，1=占用 | 供 F04 时段日历渲染 |
| 实验室列表 | JSON：实验室ID、名称、位置、状态 | 供筛选与 F09 维护 |

### 4.5 算法

1. 设备状态推导算法：若存在状态为“使用中”且当前时间在其时段内的预约则显示“使用中”；否则若存在状态为“待审批/已批准”且结束时间在未来的预约则显示“已预约”；否则若设备维护标志为真显示“维护中”；否则显示“空闲”；
2. 时段占用切分算法：查询该设备全部有效预约（状态∈{待审批,已批准,使用中}），对每条预约按30分钟粒度切分为槽位区间，与实验室开放时段求交后标记占用；开放时段之外的槽位标记为“不可预约”，不参与冲突判断；
3. 关键词搜索算法：对名称、型号执行 LIKE '%kw%' 模糊匹配，名称精确命中与编号前缀命中优先排序，结果按状态（空闲优先）＋编号排序。

### 4.6 流程逻辑

设备浏览流程：进入 F03 → EquipmentViewModel 并行请求实验室列表与设备列表（默认第一页）→ 渲染卡片与状态标签 → 用户切换筛选/翻页时带参重新查询 → 下拉刷新强制重新拉取状态。

时段日历流程：F04 加载 → 请求该设备近14天占用表 → 与开放时段合并渲染 → 已占用槽位置灰、可预约槽位高亮 → 用户点选槽位进入预约页并预填起止时间。

## 5　预约管理模块（M03）设计说明

### 5.1 模块描述

本模块实现《需求说明书》FR-03：在线预约申请、时段冲突检测、我的预约查询与取消预约，是系统核心业务模块。后端程序单元为 routers/reservation.py、services/reservation_service.py、repos/reservation_repo.py；客户端程序单元为预约申请页 F05、我的预约页 F06 及 ReservationViewModel。涉及数据表：t_reservation（预约记录，含业务编号）、t_equipment、t_user；并调用 M05 生成“新预约待审批”通知。预约状态流转遵循《需求说明书》3.3节流转表，受控迁移，禁止跳变。

### 5.2 性能

1. 冲突检测耗时不超过500毫秒（NFR-P3），冲突判断在数据库层完成（时间区间条件查询＋唯一性兜底索引）；
2. 预约提交（含事务写库与通知生成）不超过2秒（NFR-P1）；
3. 我的预约分页查询不超过1秒，依赖（申请人ID、状态、创建时间）组合索引。

| 取消结果 | 统一返回体 | 成功后同步通知管理员（M05） |

### 5.5 算法

1. 时段冲突检测算法（核心）：对目标设备与目标区间 [S, E)，查询 t_reservation 中同设备且状态∈{待审批,已批准,使用中}的记录，满足条件 NOT（已有.end ≤ S OR 已有.start ≥ E）即判为区间重叠冲突；同时查询本人全部有效预约做同样的重叠判断（BR-03、BR-04）；命中任一冲突则返回409并给出具体原因，申请不写库；
2. 业务规则校验算法：依次校验 BR-01（时长30分钟～8小时）、BR-02（提前1～14天）、BR-03（本人有效预约≤3条）、BR-04（设备时段唯一）；全部通过方可进入冲突检测；
3. 业务编号生成算法：编号＝YYMMDD＋当日预约序号（4位右补零），序号取自当日最大序号＋1，在事务内加行锁生成，保证唯一。

### 5.6 流程逻辑

预约提交流程：F05 预填设备与时段（来自 F04 日历点选）→ 客户端校验（同一天、粒度30分钟）→ POST /api/reservations → 服务端规则校验（BR-01/02/03）→ 冲突检测（BR-04）→ 通过则事务内：写入 t_reservation（状态=待审批、生成业务编号）→ 调用 M05 通知管理员 → 返回成功；任一环节失败整体回滚并返回409/400。

取消流程：F06 点选“取消”→ 确认对话框（NFR-U2）→ PUT /api/reservations/{id}/cancel → 归属与状态校验 → 时限校验（距开始≥2小时自助取消；不足2小时提示联系管理员）→ 状态置“已取消”→ 调用 M05 通知管理员 → 刷新列表。

### 9.5 算法

1. 使用率计算算法：设备使用率＝Σ实际使用时长 ÷（设备数×统计期内日开放时长）×100%；实际使用时长＝归还时间－签到时间（按有效“已完成”记录聚合）；开放时长取实验室开放时段配置；
2. 违约率与通过率算法：违约率＝违约记录数 ÷ 已批准预约数 ×100%；审批通过率＝批准数 ÷（批准数＋拒绝数）×100%；分母为0时返回空值并在前端显示“无数据”；
3. 分组聚合算法：按所选粒度（日/周/月）对时间字段格式化分组，结合实验室/类别条件过滤，在 SQL 层完成 COUNT/SUM 聚合，Python 层仅做比率计算与序列组装。

### 9.6 流程逻辑

统计查询流程：F10 设置筛选条件 → ChartViewModel 请求对应指标接口 → 服务端聚合计算 → 返回数据序列 → ChartViewModel 映射为 Qt Charts 数据集（使用率/违约率用柱状图、预约量趋势用折线图、类别占比用饼图）→ 渲染；切换指标页签仅重新拉取对应序列。

导出流程：点击导出 → 携带当前筛选条件请求导出接口 → 服务端流式生成 CSV → 客户端弹出保存对话框 → 写入本地文件并提示成功。
